01 The Problem

Every presenter is also a slide operator, and it shows.

Watch anyone present and you will see the same tax being paid: a hand on a clicker, a glance down to check what is next, a lost half-second reconnecting with the room. The speaker's attention is split between the argument they are making and the machinery displaying it.

The obvious fix — let the deck listen — sounds trivial and is not. It requires deciding, several times a second, whether the words currently coming out of someone's mouth mean "move on" — and being confident enough to act, but not so confident that a passing mention of a later topic throws the presentation across the room.

02 Architecture

The obvious architecture is impossible. That was the finding.

Office.js — Microsoft's supported way to extend PowerPoint — cannot control the slideshow engine while PowerPoint is in fullscreen presentation mode. That is a confirmed platform limitation, not a bug to be worked around, and it invalidates the single-component design anyone would reach for first.

So the system runs as two components in two different runtimes, and stays that way on purpose:

  • An Office.js add-in (React / TypeScript) owning speech capture, the NLP matcher, the UI and command handling — everything that lives in a browser runtime.
  • A C# VSTO COM bridge exposing a local HTTP API, which is the only thing on the machine able to drive fullscreen navigation.

They cannot be merged — browser and COM/.NET are not the same world — so the design leans into it with a graceful fallback chain: try the VSTO bridge, fall back to goToByIdAsync, fall back again to setSelectedSlides. The presenter never sees which path fired; they only see the slide change.

"Four hours of documentation to establish that the clean architecture was impossible, then a fortnight making the ugly one feel invisible. That ratio is normal, and worth budgeting for."

03 Speech → Slide

TF-IDF, a rolling window, and two guards against false confidence.

Live speech is scored against every slide's text with TF-IDF and cosine similarity — stop-words filtered, tokens stemmed. It runs in under ten milliseconds and costs nothing to operate, which matters when the decision has to be re-made continuously for forty minutes.

Three design decisions did most of the work:

  • A 30-word rolling window. Without it, accumulated transcript text drags matches toward whichever slide has the most words in common with the last five minutes. Bounding the context was the single highest-impact fix in V1.
  • Score interim results, not just final ones. Waiting for complete sentences produced navigation that was correct but visibly late. Interim results made it feel real-time — with only final results allowed to reset the match counter, so one ambiguous fragment can't break a valid streak.
  • Two guards, both necessary. A consecutive-match requirement kills single-frame false positives; a cooldown between navigations stops the deck oscillating between two similar slides. Neither alone is sufficient — that took experimentation to establish.

The known weakness is honest and documented: TF-IDF matches words, not meaning. Say "let's talk about revenue" over a slide titled "Q3 Financial Results" and it has nothing to work with. That single failure mode is the entire motivation for V2's semantic matching upgrade.

04 The Hard Parts

Four rejected approaches before one worked.

The zoom feature — magnifying part of a slide on command — looked like a small addition and consumed the most engineering of any single feature. Four approaches were built and abandoned:

  • GotoClick(x, y) — wrong API entirely. It takes an animation index, not coordinates.
  • Simulated keystrokes — only continues an existing zoom; it cannot start one.
  • The Windows Magnification API — magnifies the entire screen, window chrome included. Correct behaviour, unusable result.
  • P/Invoke toolbar automation — worked on one machine, then broke on the next resolution and DPI combination.

What finally worked was a change of category rather than a better hack: a Morph transition between hidden duplicate slides. Entirely inside PowerPoint's own rendering engine, so it looks professional and behaves identically on every machine.

The Pattern

Three of the four failures were attempts to make the host application do something it does not expose. The solution was to stop fighting the platform and express the feature in primitives it already had. That generalises well beyond PowerPoint.

06 What I Learned

In a real-time system, the guards are the product.

Key Takeaways
  • Bound your context before you improve your model. The 30-word window beat every matcher tweak that preceded it. Most accuracy problems in live systems are context problems wearing a model problem's clothes.
  • Latency is a feature with a threshold. Correct-but-late navigation read to users as broken. Moving to interim results changed nothing about accuracy and everything about whether people would use it.
  • Know the platform's real limits early. The two-runtime architecture wasn't a preference; it was the only shape that worked. An afternoon spent proving that saved a rewrite.
  • Name the failure mode you can't fix yet. Writing down that TF-IDF cannot handle paraphrase turned a vague dissatisfaction into V2's single clearest requirement.

V2 in progress: replacing keyword matching with semantic retrieval so paraphrased speech resolves to the right slide — the one failure mode V1 documented and could not solve within its architecture.
